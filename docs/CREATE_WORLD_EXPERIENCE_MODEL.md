# Create World Experience Model

## Purpose

This document defines how a creator should experience Dropple's `Create World`.

It does not define:

- UI layouts
- component placement
- shell architecture
- routing
- implementation details

It defines the creator's progression through one persistent creative world.

This document exists to ensure that implementation decisions reinforce the same creator experience regardless of creative language.

It sits between constitutional architecture and product expression:

`LAW`
`-> Architecture`
`-> Experience Model`
`-> Product Expression`
`-> UI`

## Core Principle

A creator should never feel that they are moving between different editors.

They should feel that they are remaining inside one living creative world where meaning comes first, expression grows naturally, and their project gradually becomes the dominant presence within that world.

## Relationship to Existing Constitutional Models

The existing constitutional corpus already defines:

- `Runtime` owns canonical truth
- `Create World` owns the shared creative substrate
- `Creative Language` owns discipline-specific meaning
- `Product Expression` owns how truth becomes creator experience

This document answers a different question:

`What should it feel like to live inside that world from the first decision to a mature project?`

## Create World

The `Create World` is constant.

It is the place creation happens.

It does not change when languages change.
It does not disappear when projects mature.
It quietly supports every stage of creation.

The creator should not experience `Create World` as:

- a blank technical editor
- a workspace switcher
- a collection of panels
- a generic infinite canvas

The creator should experience `Create World` as:

- calm
- spacious
- welcoming
- alive
- meaningful
- non-intimidating

The world should feel ready, not empty.

## Experience Progression

Create World should be experienced as a progression of creator states rather than as a static interface.

## Stage 1 — Creative Direction

The creator is deciding how they want to think.

They are not yet asking:

- which tool do I use?
- where is the inspector?
- what panel do I open?

They are asking:

- what am I here to create?
- what kind of work am I beginning?
- which language or direction makes sense for this idea?

The system should communicate:

- possibility
- clarity
- confidence
- low cognitive load

The creator should feel invited into meaningful work, not pressured to operate software.

## Stage 2 — Creative Arrival

The creator has entered `Create World`.

The world is calm.
Nothing demands immediate action.
The creator understands:

`This is my creative universe.`

The world should feel:

- present
- breathable
- ready
- quiet

The UI may be visible, but it should feel like infrastructure, not like the primary subject.

The world is now the dominant visual presence.

## Stage 3 — First Expression

The creator creates something meaningful for the first time.

This should happen because the creative language naturally reaches a first expression, not because an editor requires an artifact immediately.

Examples:

- `UIUX -> First Page`
- `Graphic -> First Composition / First Artboard`
- `Education -> First Lesson`

At this moment, the project begins to exist.

The creator is no longer only orienting themselves.
They are now making something real.

This is the transition where visual authority should begin moving away from the world and toward the work itself.

## Stage 4 — Project Emergence

The creator no longer thinks only about isolated artifacts.

Relationships begin to matter.
Structure begins to matter.
Navigation begins to matter.

The project becomes something larger than its first expression.

The creator begins to think in systems such as:

- pages within an application
- compositions within a communication system
- lessons within a learning structure
- flows, relationships, and meaning across artifacts

The world now supports project growth rather than simply project entry.

## Stage 5 — Living Project

The creator feels immersed in the project.

The world still exists.
But attention now belongs primarily to the project itself.

The interface quietly supports creation.
The world hosts.
The project leads.

At this stage the creator should feel:

- continuity
- immersion
- legibility
- momentum

They should feel that their work lives inside a persistent creative universe rather than inside a temporary editing session.

## Visual Authority Principle

Visual authority should shift throughout the journey.

At different stages, different things should visually and psychologically dominate:

### Creative Direction

Visual authority belongs to:

- direction
- meaning
- invitation

### Creative Arrival

Visual authority belongs to:

- the world

### First Expression

Visual authority belongs to:

- the first meaningful artifact

### Project Emergence

Visual authority belongs to:

- the project structure and relationships

### Living Project

Visual authority belongs to:

- the living project itself

This progression means the world should welcome the creator, but the project should gradually take over.

## Progressive Revelation

Nothing should appear simply because it exists.

Everything should appear because the creator is ready for it.

This applies to:

- tools
- panels
- relationships
- guidance
- capabilities
- complexity

Meaning should always arrive before mechanics.

The creator should understand what is happening before being asked to configure how it works.

## UI as Infrastructure

The UI should remain supportive throughout the journey.

Controls, rails, inspectors, zoom surfaces, and navigation tools should be experienced as instruments.

They should:

- support orientation
- support expression
- support refinement
- support delivery

They should not become the primary product story.

The creator should not feel:

`I am inside a tool system.`

They should feel:

`I am inside my creative world, and the system is helping me think.`

## Relationship to Creative Languages

Create World provides the environment.

Creative Languages provide meaning.

This means:

- the world should feel consistent
- the language should feel distinct
- language meaning should never be erased by a universal shell aesthetic

The creator should feel they are remaining inside one world while thinking in different grammars depending on the work:

- `UIUX`
- `Graphic`
- `Application`
- `Education`
- `Systems Engineering`
- future languages

The world is shared.
The meaning changes.

## What This Document Is Not

This document is not:

- a UI specification
- a shell specification
- a routing specification
- a control layout specification
- a final visual design
- a language-specific style guide

It is a constitutional experience document.

Its purpose is to define what the creator should feel as they move through one persistent creative world.

## Product Consequence

Future implementation decisions should be evaluated with questions such as:

- what stage of the creator journey does this support?
- what should the creator be feeling at this moment?
- does this increase meaning before increasing mechanics?
- does this reinforce one living world rather than many separate editors?

This is a stronger design compass than asking only:

- where should this panel go?
- which control should be visible?
- how do we expose another feature?

## Closing Principle

Create World does not teach creators how to operate software.

Create World helps creators think.

Creative Languages help creators express.

Projects help creators discover.

The interface should quietly disappear behind that journey.
