# Product Expression Principles

## Purpose

This document is the bridge between Dropple's constitutional architecture and
its product experience.

It does not introduce new constitutional concepts.
It derives strictly from the existing constitutional corpus and defines how
frozen constitutional truth should become creator experience.

The constitution defines truth.

This document defines how truth should feel.

## Product Expression Principle

Every product experience must be explainable as the projection of one or more
frozen constitutional contracts.

## Product Expression Test

Before implementing any feature, answer:

- Which constitutional contract does it express?
- Which creator question does it answer?
- Which lifecycle transition does it support?
- What evidence proves it succeeded?

If those questions cannot be answered, the feature is probably premature.

## Creator Before Tool

Creators should think in their creative language before they think in tools.

Product surfaces should therefore introduce:

- world
- structure
- role
- intention

before exposing tool vocabulary or editing mechanics.

## Projection Before Configuration

Reveal meaning before revealing properties.

The creator should understand what something is in the creative domain before
being asked to configure how it behaves.

## Guidance Before Editing

Teach the creator what they are making before exposing how to edit it.

Product guidance should help the creator understand:

- what kind of artifact is emerging
- what comes next structurally
- why a capability is now relevant

before presenting broad editing surfaces.

## Emergence Before Complexity

Advanced capabilities should emerge only when they become meaningful.

This is especially important for:

- motion
- timeline
- review
- versioning
- system configuration

Complexity should be introduced by relevance, not by default visibility.

## One Authority, Many Assistants

Assistants may propose.

Authorities establish truth.

This applies to:

- AI
- templates
- marketplace assets
- imports
- automation
- future agents

Product experience should preserve this distinction clearly.

## Invisible Architecture Principle

The stronger the constitutional architecture becomes, the less creators should
need to perceive it directly.

The creator should never think:

`This planner is elegant.`

They should think:

`This tool understands what I'm trying to create.`

## Creators Experience Projections, Not Architectures

Creators should never need to think in terms such as:

- dispatcher
- planner
- compiler
- `BlueprintV1`
- runtime
- lifecycle
- authority

They should feel:

`This tool understands how I think.`
