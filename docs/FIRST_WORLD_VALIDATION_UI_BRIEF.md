# FIRST WORLD VALIDATION UI BRIEF

## Status

`ACTIVE IMPLEMENTATION BRIEF`

## Phase

`Validation Construction`

## Mission

Build the smallest runnable `First World` slice that can prove whether the
existing `Dropple` vision works in lived experience.

This brief does not exist to expand architecture.

It exists to produce evidence.

The question is no longer:

`What should Dropple be?`

The question is now:

`Does the existing First World vision actually work when someone can enter it?`

## Spatial Runtime Law

The `First World` is rendered as a real-time spatial environment.

The rendering technology exists to express the `Living World`, not to
redefine the application architecture.

`React` remains responsible for application structure and experience.

The `Spatial Runtime` remains responsible for spatial presence.

This does not mean:

`Dropple is becoming a 3D application.`

It means:

`The First World is rendered by a spatial runtime because the product itself is a world.`

The `Spatial Runtime` is not a `3D engine` in the architectural sense.

It is the runtime responsible for expressing spatial meaning:

- place
- orientation
- distance
- scale
- atmosphere
- movement

## Validation Slice

The `First World Validation UI` is one vertical slice:

`Browser`

`-> First World`

`-> Origin Region`

`-> Travel`

`-> One Creative Anchor`

`-> Minimal Authoring Experience`

`-> Same Universal Canvas`

If this slice works, later domains inherit from it.

If it fails, the failure will produce evidence strong enough to justify
reopening specific documents.

## Runtime Separation

The validation slice should be read through three cooperating layers.

### 1. Experience Layer

Owned by `React`.

Responsibilities include:

- inspector
- context panels
- commands
- dialogs
- AI surfaces
- workspace controls

### 2. Spatial Runtime

Implemented through a spatial renderer such as `React Three Fiber`.

Responsibilities include:

- camera
- `World Core`
- `Origin Region`
- `Creative Anchors`
- atmosphere
- lighting
- terrain
- travel

It does not own:

- pages
- inspector state
- forms
- creative-language semantics
- business logic

### 3. Domain Runtime

Owned by the existing runtime truth and authority systems.

Responsibilities include:

- project state
- creative languages
- events
- memory
- history
- dispatcher
- authority

The `Spatial Runtime` does not own business logic.

It renders the living world.

## Purpose Chooses The Renderer

Meaning chooses the renderer.

Do not ask:

`Should this be 2D or 3D?`

Ask:

`What is this object's purpose?`

If it must be experienced as a place, render it spatially.

If it must be manipulated precisely, render it as an interface.

This law is purpose-based, not technology-based.

The implementation medium may change over time.

The responsibility split should not.

## Render Responsibility Classes

### Spatial Objects

Spatial objects belong to the `Spatial Runtime` because their meaning depends
on:

- distance
- orientation
- movement
- atmosphere
- scale

Examples:

- `Origin Platform`
- `World Core`
- `Creative Anchors`
- `Sky`
- `Terrain`
- `Bridges`
- `Districts`

### Precision Objects

Precision objects belong to the `Experience Layer` because their meaning
depends on:

- editing accuracy
- information clarity
- forms
- commands
- precise manipulation

Examples:

- inspector
- properties panel
- layer tree
- timeline
- prompt
- AI chat
- color picker

### Boundary Objects

Boundary objects participate in both systems.

They have:

- a spatial representation in the `Spatial Runtime`
- an interaction representation in the `Experience Layer`

Examples:

- `Creation Platform`
- `Canvas Surface`
- `Application Portal`
- `World Map`
- `Domain Entrance`

These objects do not create a rupture between world and interface.

They change the emphasis of the experience while preserving continuity.

## What This Slice Must Prove

The slice is successful only if it proves all five of these things in a
runnable experience.

### 1. Arrival Is Real

The `Traveler` arrives in a genuine `Origin Region`, not in a disguised
homepage or dashboard.

### 2. The World Is Continuous

The `Traveler` should feel they remain inside one living world at all times.

No action may feel like opening another application.

### 3. Travel Is Real

The `Traveler` must be able to move toward at least one meaningful place in
the world.

### 4. Domain Legibility Increases With Approach

At least one destination must become more understandable as the `Traveler`
approaches it.

### 5. Authoring Begins Without Breaking Continuity

A minimal authoring state must become available without making it feel like
the `Traveler` left the world or opened a separate editor.

## Scope

This validation slice includes only what is necessary to test the above
claims.

### Included

#### 1. Persistent First World

- one living world host
- one stable world/canvas continuity
- one `Origin Region`
- one `Traveler`

#### 2. Origin Region

- readable arrival place
- visible center
- visible path outward
- world beyond the origin

#### 3. Travel

- one continuous movement path from the `Origin Region` toward a destination
- no page transition behavior
- no teleport metaphor

#### 4. One Creative Anchor

The first validation target should use one anchor only:

`UIUX`

The purpose is not breadth.

The purpose is to validate continuity from world arrival into one creative
possibility.

#### 5. Minimal Same-Canvas Authoring Entry

Only enough authoring presence to prove:

- the world remains continuous
- the canvas remains invariant
- entering the domain changes meaning, not existence

### Excluded

This slice does not attempt to build:

- every `Creative Domain`
- deep revelation systems
- advanced memory systems
- complete authoring workflows
- all future travel routes
- broad polish passes
- large content inventories
- full product completeness
- physics
- collisions
- avatars
- game mechanics

## Core Laws For This Slice

### Law 1 - No New Architecture Without Blocker Evidence

No new constitutional, architectural, or model document should be created
unless implementation is blocked by a specific missing decision.

### Law 2 - Every Completed Step Must Be Runnable

Work is not considered complete until it can be run and experienced.

### Law 3 - The First World Must Feel More Real After Each Step

Every implementation task must answer:

`Does this make the First World feel more like one living world?`

### Law 4 - The Universal Canvas Remains Invariant

No step may introduce the feeling that the `Traveler` opened a different

### Law 5 - Evidence Overrides Assumption

If reality contradicts a frozen assumption, record the evidence and reopen

### Law 6 - Validation Before Completeness

Nothing is implemented because it is architecturally complete.

Everything is implemented because it validates a creator experience.

If a system is theoretically justified but not yet necessary to validate the
`First World`, it should not be built in this phase.

### Law 7 - Every Task Must Climb The Validation Ladder

Every implementation task, pull request, and Codex execution step must state
which validation it advances.

If a change does not advance at least one validation milestone in this brief,
it likely does not belong in `Validation Construction`.

### Law 8 - Spatial Runtime Is A Medium, Not A New Architecture

The validation slice may adopt a spatial runtime because the `First World`
depends on spatial meaning.

This adoption must not be treated as a rewrite of the product into a game
engine or as a replacement for the existing application/runtime authority
model.

The `Spatial Runtime` is one subsystem.

It is not the application.

## Validation Target

The validation target is intentionally small.

The experience should allow a person to:

1. open `Dropple`
2. stand in the `Origin Region`
3. recognize that they are in a place
4. see at least one meaningful distant `Creative Anchor`
5. move toward it through continuous travel
6. reach a minimal `UIUX` creative arrival state
7. remain aware that the same world and canvas are still present

That is enough to validate the foundation.

## V1.0 - Arrival Sequence

`V1 - I arrived` should be implemented first as an arrival sequence rather
than as a static screen state.

The purpose of `V1.0` is to produce the first ten seconds that make arrival
feel real.

### Step 1 - Browser Opens

Goal:

There is no impression of loading an application.

Behavior:

- full viewport
- no dashboard
- no workspace cards
- no modal
- no splash screen
- no login interruption when authentication is already valid

Instead:

the world is already present, as though the browser became a window.

### Step 2 - World Awakens

For roughly `1-2` seconds, the camera remains still.

Nothing dramatic happens.

The creator notices:

- atmosphere
- light
- distant anchors
- subtle environmental motion

The world exists without asking for interaction.

The message is:

`This place was here before I arrived.`

### Step 3 - Orientation

Without text explaining everything, the environment naturally reveals:

- a `World Core`
- the surrounding world
- distant `Creative Anchors`

The camera should not rotate automatically.

The creator should feel in control.

If guidance is needed, it must remain subtle, such as a gentle pulse or soft
light emphasis from the nearest anchor.

### Step 4 - Recognition

Within a few seconds, the creator should naturally answer:

- `Where am I?`
- `Where can I go?`
- `What is this place?`

If those answers require reading documentation, `V1` has failed.

### Step 5 - Invitation

Only after orientation should the world invite interaction.

Not with:

- a popup
- a tutorial
- an instructional overlay

Instead with something simple:

- a highlighted path
- a living `Creative Anchor`
- a softly animated distant invitation

The invitation should feel like curiosity, not instruction.

### Step 6 - Control

The creator can now:

- pan
- zoom
- rotate, if rotation belongs to the current world model
- hover over a `Creative Anchor`

This is the first moment where the creator actively participates.

## Validation Ladder

Every implementation step must explicitly target one of the following
validations.

| Validation | Experience | Implementation Goal |
| --- | --- | --- |
| `V1` | `I arrived.` | Render the `Origin Region` and establish the initial camera. |
| `V2` | `I understand where I am.` | Make the `World Core` readable and reveal the surrounding world. |
| `V3` | `I see possibilities.` | Place the `Creative Anchors` so they are visible from the `Origin`. |
| `V4` | `I can travel.` | Implement continuous movement from `Origin` to the `UIUX` anchor. |
| `V5` | `I never left the world.` | Transition into the `UIUX` district without changing routes or opening another application. |
| `V6` | `I can create.` | Allow creation of the first `Page` on the same `Universal Canvas`. |

If a task cannot point to one row in this ladder, it should be deferred until
after the `First World Experience Review`.

## Done Conditions

Each validation must have a binary completion condition.

### V1 - I arrived.

Done when:

- opening `Dropple` always lands in the `Origin Region`
- the world is visible immediately
- the creator feels placed somewhere intentional
- no dashboard or editor UI appears first
- the `Origin Region` is visually readable
- the `World Core` is recognizable
- at least one `Creative Anchor` is visible from the `Origin`
- the world feels alive before any interaction
- the creator can begin exploring without instructions

### V2 - I understand where I am.

Done when:

- the `World Core` is readable as the center of arrival
- the surrounding world is visible enough to establish place
- the creator can perceive that the world extends beyond the origin
- the scene feels intentional rather than empty

### V3 - I see possibilities.

Done when:

- at least one `Creative Anchor` is visible from the `Origin`
- the anchor reads as a place, not a menu item
- the anchor invites curiosity before explanation
- the creator can tell there are other directions to create

### V4 - I can travel.

Done when:

- selecting the `UIUX` anchor begins continuous movement
- the camera never teleports
- the world remains visible throughout
- travel can be interrupted or skipped after the first experience if needed

### V5 - I never left the world.

Done when:

- the `Traveler` reaches the `UIUX` district
- the environment remains continuous during approach and arrival
- no route change or application-switch feeling occurs
- the same `Universal Canvas` remains perceptible

### V6 - I can create.

Done when:

- the creator reaches the `UIUX` district
- a first `Page` can be created
- the `Page` appears as part of the same world/canvas continuity
- there is no transition into a separate editor

## First Anchor

The first anchor for validation should be:

`UIUX`

Reason:

- it already has the most mature downstream implementation surface
- it is sufficient to prove same-world authoring continuity
- it can validate whether a creative domain can be entered without breaking
  the world illusion

This does not privilege `UIUX` as the final center of Dropple.

It is simply the first validation anchor.

## Mission Format

Implementation work in this phase should be assigned as validation missions,
not as broad feature requests.

Example:

`Mission: V1.0 - Arrival Sequence`

`Implement only the First World arrival experience required to satisfy the V1 done conditions.`

That mission includes:

- rendering the `Origin Region`
- establishing the initial camera
- rendering the `World Core`
- displaying placeholder `Creative Anchors` in the distance
- adding subtle environmental animation such as lighting, atmosphere, or
  ambient movement
- allowing basic camera navigation

It does not include:

- travel
- `UIUX` district entry
- authoring
- new architecture

## V1.1 - Spatial World Runtime

After `V1.0 - Arrival Sequence`, the next rendering mission is:

`V1.1 - Spatial World Runtime`

The mission is not:

`Adopt Three.js because 3D is impressive.`

The mission is:

`Render the Living World spatially because Dropple is a world.`

`React Three Fiber` is the current implementation medium, not the product
identity.

The goal is not to make people think:

`Now I am in Three.js.`

The goal is to make people feel:

`I am still in Dropple.`

### V1.1 Scope

Only the following should exist in the first spatial runtime slice:

- `Origin Platform`
- `World Core`
- `Atmosphere`
- `Sky`
- `Terrain`
- `Lighting`
- `Camera`
- three `Creative Anchors`
- hover interaction
- minimal world-preserving overlay support if needed for validation

Nothing more.

### V1.1 Travel Model

The camera is the `Traveler`.

Avoid building a player character in this phase.

Allowed movement language:

- orbit
- glide
- focus
- zoom
- simple cinematic travel

### V1.1 Life Rule

The world should remain alive even when the creator does nothing.

Examples:

- clouds drift
- particles move
- sunlight changes subtly
- the `World Core` pulses
- anchors emit restrained light
- atmosphere responds to wind

This is not for spectacle.

It is to communicate that the world exists independently of the creator's
action.

### V1.1 Experiential Success Criterion

The creator should never consciously think about the renderer.

They should not feel:

- `Now the app became 3D.`
- `Now React took over.`
- `Now I entered another tool.`

They should feel only:

`I am still in Dropple.`

## Task Selection Rule

From this point forward, every implementation task should be selected by one
question:

`Will this make the First World more testable by a real person?`

The first question is no longer:

`Is this a good idea?`

It is:

`Which of the six validations does this improve?`

If the answer is no, the task is likely planning drift.

Examples:

Bad:

- define another First World theory
- write another broad behavior speculation
- introduce a new planning track without a blocker

Good:

- make the `Traveler` move from `Origin Region` toward the `UIUX` anchor
- make the anchor become more legible during approach
- preserve same-canvas continuity during creative arrival
- enable creation of one first `Page` without breaking world continuity

## Implementation Sequence

The slice should be built in this order.

### Step 1 - Origin Region Arrival

Confirm the `Traveler` can enter and orient within a real `Origin Region`.

### Step 2 - Anchor Visibility

Make the first `Creative Anchor` visible and legible enough to invite
approach.

### Step 3 - Continuous Travel

Implement movement from the `Origin Region` toward the anchor as travel, not
navigation.

### Step 4 - Domain Approach

As the `Traveler` nears the anchor, domain meaning should become more
perceivable without collapsing into UI-first explanation.

### Step 5 - Minimal Same-Canvas Authoring

Enter a minimal `UIUX` authoring condition without breaking the persistent
world and canvas continuity.

Placeholder geometry, simple lighting, primitive structures, and basic camera
movement are acceptable in this phase if they are sufficient to validate
continuity, arrival, travel, and same-world creation.

Visual ambition must not delay evidence.

After `V6`, the next major checkpoint should be:

`First World Experience Review`

Its purpose is not code inspection.

Its purpose is evidence review.

It should answer:

- did creators understand where they were?
- did travel feel natural?
- was continuity obvious?
- did anyone feel like they opened another application?

The next major architectural document should be written only after the team

In this phase, reality has priority over speculation.

## Success Criteria

The `First World Validation UI` is successful when:

- the `Traveler` arrives somewhere real
- the world feels continuous
- at least one `Creative Anchor` invites approach
- travel feels more like journey than navigation
- minimal `UIUX` authoring begins without world rupture

## Failure Criteria

The validation slice has failed if any of these occur:

- entering the domain feels like opening another application
- movement feels like page switching
- the world disappears when authoring begins
- the canvas feels replaced instead of continuous
- the anchor is only understandable through interface explanation

Failure is acceptable.

Unvalidated architecture drift is not.
